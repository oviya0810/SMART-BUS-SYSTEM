# SMARTBUS 360 — Security & Privacy

## Implemented controls
| Area | Implementation |
|---|---|
| Passwords | Werkzeug **scrypt** hashes; policy ≥ 8 chars with letters + digits, not equal to username; never logged, exported or returned after creation. Audit details are scrubbed of password/token keys. |
| First login | Student and bus accounts are created with `must_change_password`; every API except `/api/auth/*` returns `403 PASSWORD_CHANGE_REQUIRED`, and Socket.IO refuses the connection, until changed. |
| Sessions | Signed, `HttpOnly`, `SameSite=Lax` cookie, 12 h lifetime, `Secure` flag configurable for HTTPS. A per-user `session_version` invalidates every session on password change, reset or deactivation. |
| CSRF | Per-session random token returned at login, required in `X-CSRF-Token` for every state-changing request (constant-time compare). Mutations also require `application/json`, which HTML forms cannot send cross-site. |
| Login abuse | Sliding-window limiter per IP+username (5 failures / 15 min → `429`); identical error for unknown user and wrong password; dummy hash to equalise timing. |
| Authorization | Role decorator on every route (admin / student / bus). The student or bus is always derived from the session, never from IDs in the request. Cross-bus requests return `404` (no existence leak). |
| Devices | Per-device random 256-bit token (`secrets.token_urlsafe(32)`), stored only as SHA-256, shown once, rotatable, revocable. Every payload must name the device's own bus (`403 DEVICE_BUS_MISMATCH`). Disabled or unassigned devices are refused. |
| Realtime | Socket.IO connections are authenticated from the session cookie; rooms are assigned server-side by role (admin / own bus / own student). Origin policy: same origin or configured `CORS_ORIGINS` only. |
| Privacy | Student phone locations go only to admins; pickup locations only to the assigned bus and admins; register numbers are not sent to the bus pickup list; students see a public incident view without staff notes. Location is read only when the student taps a button. |
| Input validation | Explicit validators for every field (types, ranges, lengths, patterns), coordinate sanity (rejects 0,0 and out-of-range), occupancy ≤ capacity, ADC 0–4095, timestamp skew limits. SQLAlchemy ORM parameterises all SQL. Request body ≤ 1 MB. |
| Errors & logs | Uniform JSON errors; unexpected exceptions return a generic message while the stack trace goes to `backend/logs/smartbus360.log` (rotating). |
| Headers | `X-Content-Type-Options`, `X-Frame-Options: DENY`, `Referrer-Policy`, `Permissions-Policy`, `Cache-Control: no-store` on the API, and a Content-Security-Policy on the dashboards. |
| CSV export | Formula-injection characters (`= + - @`) are neutralised. |
| Audit | Logins, failed logins, account changes, device provisioning/rotation, pickup transitions, incidents, alcohol warnings, rejected telemetry — with actor, IP and time. |
| Secrets | `SECRET_KEY` from `.env` (generated by setup) or auto-generated into `backend/instance/secret_key`. No production credentials are hardcoded; the first admin is created interactively. |

## Local network limitations — read this
* **HTTP is not encrypted.** On plain `http://bus.local`, anyone on the same Wi-Fi who can sniff traffic could read
  session cookies, passwords during login, student locations and device tokens. WPA2/WPA3 Wi-Fi encryption protects
  against outsiders but **not** against other users on the same network.
* Use **HTTPS** (see NETWORK_SETUP §6) whenever students or staff use shared Wi-Fi, and set `SESSION_COOKIE_SECURE=true`.
  HTTPS is also required by browsers for phone GPS.
* ESP32 devices send their token with every request. Prefer: a separate WPA2 SSID/VLAN for bus devices, HTTPS from
  the ESP32 (`WiFiClientSecure` with the server certificate pinned), or at minimum rotate device tokens if a device is lost.
* Buses outside campus Wi-Fi need a path to the server (4G router + VPN such as WireGuard/Tailscale into the LAN).
  **Do not** port-forward this server directly to the internet.
* The bundled server is Werkzeug's threaded server with WebSocket support — appropriate for a campus LAN with tens of
  buses and hundreds of users. For larger or internet-facing deployments put it behind a reverse proxy (nginx/Caddy)
  with TLS and run it as a Windows service (e.g. NSSM).
* The login rate limiter is in-memory (resets on restart, single process).
* Keep Windows updated, restrict who can log in to the server PC, and protect `backend/instance/` (database, secret key)
  and `backups/` with NTFS permissions. Backups contain personal data.

## Alcohol sensor disclaimer
The MQ-3 module reports a raw analog value that depends on temperature, humidity, warm-up, calibration and other
gases. SMARTBUS 360 only compares it to a configurable threshold and labels the result *Warning*. It does **not**
measure blood alcohol concentration and does not prove intoxication. Warnings must be verified by a person following
the institution's procedure.
